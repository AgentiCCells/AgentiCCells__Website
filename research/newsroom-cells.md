## The main idea in one paragraph (researcher's reading)

Over 15 and 16 November Dinis moved the centre of AgentiCCells from size to the cell. Size is how a buyer understands the price; the cell is how a buyer thinks about the problem. A cell is one focused job with an objective, a deliverable and a behaviour policy, plus as many parts as the job needs. Every website is a cell, and so is Claude replying to email. Each cell gets its own page and four ways to start. The catalogue grows one need at a time, often in an industry's own words. The team should work in cells first. The site factory and the Odoo and email work are the evidence that cells with real parts can be made.

## A proposed cell format (proposal)

This is a proposal for "What to build next" item 1 of "The cell is the unit": "a folder with the objective, the deliverable, the behaviour policy, the recipe and the parts, the same for every cell." It is not agreed and nothing is built. I have used the shape of the factory's request folder (`site.json`, `brief.md`, `status.json`, article 18) as the model, because the newsroom already uses it.

```
cells/<slug>/
  cell.json          the facts, as data: slug, name, one-line objective, tiers, status, price, parts, links
  objective.md       the one job, in a sentence the customer would use
  deliverable.md     what you have at the end of each day, week or run
  policy.md          behaviour policy in plain words: reach, mandate, gap, barrier; tier by capability
  recipe.md          the free way: brief, policy and steps, to run with your own Claude
  parts.md           what the cell is made of: session, vault, repository, site, lanes, schedule, connector, owner
  examples.md        real examples with consent recorded, or "none yet"
  industries/<name>.md   optional: the same cell in one industry's words
  status.json        written by the build: not built, brief only, prototype, run by hand, live
```

`cell.json`, as a proposal:

```
{
  "slug": "website-you-steer",
  "name": "A website you steer",
  "objective": "A public site that you change by asking, from your browser.",
  "status": "first proposal, not yet sold",
  "ways_to_start": {
    "free": {"recipe": "recipe.md"},
    "our_agent_helps": {"status": "not yet a service"},
    "we_help": {"price": "£1,500", "price_status": "first proposal"},
    "we_set_it_up": {"price": "£500", "price_status": "first proposal"}
  },
  "parts": ["claude session", "repository", "website", "vault lane", "key", "schedule", "owner"],
  "tiers_used": ["change its own work", "change a system of record"],
  "sources": [{"article": "atomic-cells-end-to-end", "date": "2026-11-15"}]
}
```

Rules the format should keep, from CLAUDE.md and the articles:
- Every price carries `price_status`; every number carries a source; a thing that does not exist says so in `status`.
- `examples.md` names no customer without consent on record. The sites loop's standing rule applies: nothing for the client site that must not be listed.
- `policy.md` states each action's tier and what enforces it, and says "expectation" where only a rule stands in the way (article 12; content/method.md already does).
- A cell's status is one of: brief only, prototype, run by hand, live. No cell is "live" until it has run for someone.

The page template (next item 2 in the article) is then generated from the folder: the left column is `objective`, `deliverable`, `examples`, `policy`; the side column is the four ways to start. That keeps the data/ plus build/ pattern the site already uses (`data/cells.json`, `{{ladder}}`).
